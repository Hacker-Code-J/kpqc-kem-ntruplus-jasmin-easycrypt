# NTRU+768 complete mixed Decaps entry point

`ntruplus768_decaps(ss, ct, sk)` executes the complete decapsulation sequence
using Jasmin kernels, C orchestration and the pinned official C SHAKE256.
Its public header is `ntruplus/c/768/ref/decap_complete.h`.

## Interface and result

The three external regions must be mutually disjoint and accessible for
their full lengths. `ss` is a writable 32-byte output; `ct` and `sk` are
initialized, read-only arrays of 1152 and 2336 bytes. The first 2304 secret-key
bytes contain two encoded polynomials; the final 32 bytes supply the HashH
suffix. The functional specification accepts arbitrary input bytes and does
not assume that the suffix was generated as `HashF(pk)`.

The entry guard checks `ct`, the first key polynomial and the second key
polynomial in that order. Rejection skips all subsequent computations,
writes 32 zero shared-secret bytes and returns one. Accepted encodings
continue through the actual candidate, `r2` and message procedures. Even if
SOTP decoding fails, the implementation executes the following tail:

1. Jasmin prepares `0x02 || msg[0..95] || sk[2304..2335]`.
2. Official C SHAKE256 maps this 129-byte input to 224 output bytes.
3. Jasmin CBD1 consumes output bytes `32..223`; NTT and serialization
   regenerate the 1152-byte polynomial encoding.
4. Jasmin compares the regenerated bytes with the retained `r2` serialization,
   ORs comparison failure with SOTP failure, and masks the first 32 hash bytes.

Final acceptance requires both successful SOTP decoding and equal serialized
arrays. It returns zero and the candidate shared key. Every rejection returns
one and an all-zero shared secret. In particular, this target uses explicit
rejection; it does not return a pseudorandom fallback key on failure.

## Actual procedures and formal composition

Four new Jasmin exports complete the preceding stages:

| Source | Contract |
| --- | --- |
| `decap_hash_h_prepare.jazz` | Exact 129-byte domain/message/suffix input |
| `poly_cbd1.jazz` | Each coefficient is the difference of two hash bits, hence a trit |
| `decap_finish.jazz` | Binary final status and exact 32-byte copy-or-zero output |
| `decap_clear.jazz` | All 13506 bytes of the designated caller region become zero |

Their `*_checked` proof directories establish exact results for the actual
extracted procedures and prove termination. These results are separate from
the older HashH/CBD1 value specifications and handwritten verify/fail/mask
procedure models.
The finish proof relates its extracted comparison helper to the earlier
verify model before composing the failure flag and shared-secret mask.

`ntruplus/proof/768/ref/decap_complete/` defines the full 2336-byte key-array
layout, the regeneration and final decision, and a caller that invokes the
actual extracted procedures. `CompleteCore(G,H)` models the computation;
`CompleteDecaps(G,H)` follows it with the actual clear procedure on a supplied
workspace array. The proved result is exact agreement with `complete_spec`,
termination and an all-zero returned workspace array, conditional on the
external hash contracts. It covers both guard rejection and later failure.

The CBD1 range closes the reused NTT and serializer premises. Its trit output
also permits reuse of the existing source-audited trit-input correspondence
certificate for the official NTT's changed reduction schedule. That
certificate and native comparisons remain distinct from a C-AST equivalence
theorem; the EasyCrypt proof concerns the actual Jasmin schedule.

## External calls and cleanup boundary

HashG and HashH use the C SHAKE256 implementation pinned at
`3991b2ae08d6f0008d37e41b8aceaaab27b4ec89`. The formal composition requires
the respective 1153-to-192-byte and 129-to-224-byte hash modules to produce
the FIPS202 output and terminate. Mathematical SHAKE instances discharge
these contracts only for their models. They do not prove the native C hash
implementation or its memory and ABI behavior. The C caller's orchestration,
pointer offsets, disjointness and correspondence with the array caller also
remain external proof obligations, supported separately by source checks
and native tests.

The C wrapper zero-initializes its workspace fields. The struct contains
seven 1536-byte polynomial arrays, the 96-byte message, two 1152-byte
serializations, a 129-byte hash input and a 224-byte hash output. Static
assertions fix the field offsets, two-byte alignment and total size of 13506
bytes, including the final padding byte. Every exit calls the actual Jasmin
clear routine over that entire region.

The standalone clear theorem establishes zeros throughout its designated
array, regardless of initial contents. The formal full caller always invokes
it after the computation. Its workspace array is not a formal encoding of
the C struct fields used by every preceding call; therefore this result does
not prove erasure of all intermediate secrets in native memory. It also does
not cover registers, spills, or nested-call stacks. The message wrapper's
private HashG buffers retain their separate C `secure_clear` boundary.

## Verification status and scope

The full default replay passed 39 EasyCrypt main files, including the proofs
of 61 new lemmas. It used `Proofs:check`, no proof cache, semantic end-of-file
guards and two unfinished-proof negative controls, both rejected. Only the
recorded `proof_mains` inventory is fresh main-level replay evidence; other
imported theories retain their prior evidence and are bound by source hashes.
The run also passed 22 exact fresh extracted files, 13 negative gate controls,
and default safety and CT/SCT checks for all four new Jasmin slices. Inputs
were unchanged throughout replay.

Each normal and UBSan native run passed:

- 100 official KATs, 4622 malformed-encoding API pairs and 356 canonical-
  encoding pairs, including 192 SOTP failures and 32 later comparison failures;
- eight initial shared-secret patterns, yielding 79648 calls across official
  and new Decaps and 39824 checks that the new caller workspace was cleared;
- 4267 independent CBD/NTT/serialization cases, 1280 HashH cases, 18690 final
  comparison/mask cases and 22 direct clearing cases;
- 263 independent full-API cases, including 260 accepted entry guards whose
  two actual SHAKE input/output pairs agreed with Python `hashlib.shake_256`.

The tests check complete input preservation, canaries, binary status, exact
outputs, zero randomness consumption and call order. All 65536 two-byte CBD
inputs occur across 683 batches; this does not enumerate every polynomial
vector or every byte pair at every coefficient position. UBSan instruments
C execution, not the assembled Jasmin code.


Options and evidence details are in
[`tests/ntruplus768/decap_complete/README.md`](../tests/ntruplus768/decap_complete/README.md).
Partial runs retain explicit partial statuses. The default safety checker
initializes exported arrays, including outputs. Source absence of incoming-
output reads and functional independence from initial output values are
separate facts.

Slice safety and CT/SCT results do not establish whole mixed-API safety or
CT/SCT, nor the information-flow policy of the C entry branch. The existing
guard's two key-encoding validity disclosures retain their stated canonical-
key conditions. Functional agreement with this complete decapsulation
specification does not by itself establish key-generation relations,
encapsulation/decapsulation agreement or its failure bound, complete KEM
correctness, or classical-ROM IND-CCA security.
